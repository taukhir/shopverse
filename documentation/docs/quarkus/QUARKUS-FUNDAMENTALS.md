# Quarkus Foundations

## 1. Recognize The Project

A Maven project usually imports the Quarkus platform BOM and applies the Quarkus
Maven plugin. Features are added as extensions rather than assembled from
uncoordinated library versions.

```xml
<dependencyManagement>
  <dependencies>
    <dependency>
      <groupId>io.quarkus.platform</groupId>
      <artifactId>quarkus-bom</artifactId>
      <version>${quarkus.platform.version}</version>
      <type>pom</type>
      <scope>import</scope>
    </dependency>
  </dependencies>
</dependencyManagement>

<dependencies>
  <dependency>
    <groupId>io.quarkus</groupId>
    <artifactId>quarkus-rest-jackson</artifactId>
  </dependency>
  <dependency>
    <groupId>io.quarkus</groupId>
    <artifactId>quarkus-arc</artifactId>
  </dependency>
</dependencies>
```

The committed project is authoritative. Do not replace its BOM version with the
version from a tutorial without reviewing Java support, extension compatibility,
deployment policy, and migration notes.

## 2. Understand Extensions

An extension supplies runtime libraries plus build-time integration. Examples
include REST and Jackson, Hibernate ORM, PostgreSQL, Kafka, OIDC, health, metrics,
and OpenTelemetry.

Ask four questions about every extension:

1. Which business or operational capability needs it?
2. What build-time processing does it add?
3. Which configuration and runtime resources does it create?
4. What is its blocking, reactive, native-image, security, and upgrade behavior?

List project extensions with the project wrapper:

```powershell
.\mvnw.cmd quarkus:list-extensions
```

Review the effective dependency graph when diagnosing conflicts:

```powershell
.\mvnw.cmd dependency:tree
```

## 3. Build-Time Augmentation

Traditional frameworks often discover and wire substantial metadata at startup.
Quarkus indexes application classes and performs much of its framework assembly
during the build. The result is generated bytecode and metadata tailored to the
selected extensions and application.

Consequences include:

- faster startup is possible because less discovery remains for runtime;
- extension and application classes must be visible to the build;
- some settings affect augmentation and require a rebuild;
- unregistered reflection, resources, dynamic proxies, or class loading can
  become native-image issues;
- a successful JVM test does not prove the optional native artifact behaves the
  same way.

## 4. Developer Mode

Start continuous development mode:

```powershell
.\mvnw.cmd quarkus:dev
```

Developer mode supports live reload and developer tooling. It can also start
supported dependency containers through Dev Services when configuration is
missing and a container runtime is available.

<DocCallout type="mistake" title="Development convenience is not production evidence">

Dev mode, the Dev UI, permissive test identities, automatically created
databases, and development-only configuration must not leak into production.
Always run the packaged artifact using production-like configuration and
dependencies before release.

</DocCallout>

## 5. Configuration Profiles

Quarkus recognizes profiles such as `dev`, `test`, and `prod`. A profile-specific
property uses a `%profile.` prefix:

```properties
checkout.timeout=2s
%dev.checkout.timeout=10s
%test.checkout.timeout=100ms
%prod.checkout.timeout=2s
```

Profiles are selectors, not a secrets store. Inject secrets through the approved
secret manager or runtime environment and prevent them from appearing in source,
logs, build layers, test reports, or diagnostic endpoints.

## 6. Package And Run On The JVM

```powershell
.\mvnw.cmd clean verify
.\mvnw.cmd package
java -jar target\quarkus-app\quarkus-run.jar
```

The default fast-jar layout includes the application runner and dependency
directories under `target/quarkus-app`. Copy the complete directory when building
a container unless the project uses another supported packaging type.

Production verification should cover:

- startup with production profile configuration;
- readiness only after required initialization;
- graceful termination and in-flight request behavior;
- database, broker, identity provider, and downstream connectivity;
- memory limits, CPU limits, connection pools, thread pools, and timeouts;
- expected log, metric, and trace emission.

## 7. JVM Versus Native

| Choice | Strengths | Costs and risks |
|---|---|---|
| JVM fast-jar | mature JVM diagnostics, dynamic behavior, simpler builds, strong warmed throughput | JVM startup and memory characteristics must be measured |
| Native executable | potentially faster startup and lower memory for suitable workloads | slower and heavier build, closed-world constraints, reflection/resource registration, different diagnostics |

Choose from workload evidence. Long-running checkout services may value JVM
diagnostics and warmed performance; scale-to-zero or dense workloads may value
startup and memory. Test both only when the deployment decision warrants the
extra build and test matrix.

## 8. First Exercise

Create or locate a health-style endpoint:

```java
package example.checkout;

import jakarta.ws.rs.GET;
import jakarta.ws.rs.Path;
import jakarta.ws.rs.Produces;
import jakarta.ws.rs.core.MediaType;

@Path("/hello")
public class HelloResource {

    @GET
    @Produces(MediaType.TEXT_PLAIN)
    public String hello() {
        return "quarkus-ready";
    }
}
```

Verify it in developer mode, then package and run the fast-jar. Explain which
parts came from Jakarta REST, which came from a Quarkus extension, and which work
happened during the build.

## Common Beginner Errors

- using globally installed Maven instead of the committed wrapper;
- mixing extension versions outside the platform BOM without justification;
- treating every endpoint as reactive because Quarkus uses Vert.x internally;
- using `dev` configuration as a production baseline;
- copying credentials into `application.properties`;
- building only the native artifact and skipping normal unit and JVM integration
  feedback;
- assuming live reload proves packaged-artifact behavior.
